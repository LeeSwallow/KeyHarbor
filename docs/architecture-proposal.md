# KeyHarbor 로컬 우선 아키텍처 제안

상태: 설계 초안 · 2026-10-28. 구현, 부하 테스트, 암호화 감사 전의 제안이다. [선행 조사](open-source-research.md)의 두 프로젝트는 참고 사례다.

## 결론과 범위

- Rust CLI + 로컬 파일시스템 + SQLite를 기본으로 한다. 상시 서버는 필수가 아니다.
- 브라우저는 작업용 전용 프로필로 실행하고 계정별 비밀번호는 기존 금고에 둔다. KeyHarbor는 금고의 항목 참조와 사용 권한을 관리한다.
- 필요할 때 동일 코어를 쓰는 로컬 서비스 프로세스를 실행한다. 원격 서비스는 별도 선택 사항이며 로컬 모드의 필수 의존성이 아니다.
- 첫 버전은 동일 프로필의 동시 사용을 거부한다. 서로 다른 프로필은 병렬 실행한다. 같은 계정의 프로필 복제와 동기화는 검증 전까지 지원하지 않는다.
- DB 트랜잭션만으로 실행 중인 브라우저, 디스크 프로필, 에이전트 권한을 안전하게 잠글 수 없다. 각 수명과 장애 복구를 별도로 설계한다.

## DB 선택: SQLite 우선

| 항목 | SQLite | PGlite | PostgreSQL |
|---|---|---|---|
| 배포 | 내장형 DB, 별도 DB 서버 불필요 | WASM PostgreSQL과 JS/TS 런타임 중심 | 별도 DB 서버와 운영 필요 |
| 동시성 | WAL에서 다중 프로세스 읽기와 한 writer. 트랜잭션 경합 관리 필요 | 단일 연결 기반. socket 서버는 다중 연결을 멀티플렉싱하므로 일반 PostgreSQL과 다름 | 다중 클라이언트와 서버 측 동시성 관리 |
| Rust 로컬 앱 적합성 | 직접 내장하기 쉬운 후보 | JS 런타임/서버 또는 별도 임베딩 경로 검증이 추가로 필요 | 로컬 단일 사용자에게 운영 부담 |
| 적합한 단계 | 기본 로컬 모드 | Postgres 호환 개발 환경 실험 후보 | 원격 다중 사용자 등 실제 요구가 생긴 서버 모드 후보 |

PGlite가 나쁘다는 뜻은 아니다. 하지만 현재 요구의 병목은 다중 브라우저 실행이며 DB에는 비교적 짧은 상태 변경이 많다. SQL 호환성만으로 같은 동시성 모델이 되는 것도 아니다. PGlite의 [공식 설명](https://pglite.dev/docs/about)과 [socket 문서](https://pglite.dev/docs/pglite-socket)는 WASM/JS 기반과 단일 연결 위의 멀티플렉서를 설명한다. Rust 네이티브 배포·종료·재시작·장애 시나리오는 별도 검증이 필요하다. socket 구현 문서는 SSL을 지원하지 않는다고 하므로 원격에 그대로 노출하지 않는다.

SQLite WAL은 읽기와 쓰기가 공존하지만 writer는 한 번에 하나이고 모든 접근은 같은 호스트의 로컬 파일시스템에서 이뤄져야 한다. 장기 read transaction은 체크포인트를 막아 WAL을 키울 수 있다. [SQLite WAL](https://www.sqlite.org/wal.html). 네트워크 파일시스템이나 동기화 폴더에서 DB를 여러 기기가 직접 열지 않는다. 실제 성능은 동시 에이전트 수와 기록 빈도를 정해 측정한다.

## 의존성 방향과 배포 단위

```text
 CLI / MCP / 선택형 로컬 서비스 / 미래 원격 API
                       ↓
       application: 유스케이스와 권한 판단
                       ↓
           domain: 상태, 식별자, 불변식
                       ↑
 adapters: SQLite · 브라우저 실행 · 파일 · 금고 · OS 자격증명
```

- `domain`: 세션·프로필·계정 참조·lease·인증 요청의 규칙. DB, MCP, 브라우저 라이브러리 타입에 의존하지 않는다.
- `application`: 생성, 할당, 실행, 인계, 재개, 종료, 복구 유스케이스. 각 입력 경로는 같은 유스케이스를 호출한다.
- `adapters`: SQLite와 OS 기능, 브라우저, 금고 등 실제 I/O. 도메인에 필요한 작은 경계만 구현한다. 금고 연동은 실사용이 확인될 때 추가한다.
- `interfaces`: CLI가 우선이며 MCP와 서비스 프로토콜은 추가 전달 계층이다. MCP 입력을 받은 사실 자체가 인증 또는 승인이라는 뜻은 아니다.

처음에는 하나의 Cargo 패키지 안 모듈로 시작한다. 독립 배포나 실제 대체 구현이 생기면 코어와 어댑터를 workspace crate로 분리한다. 인터페이스를 미래의 모든 저장소나 브라우저 기능에 맞춰 미리 추상화하지 않는다. `Cargo.lock`, Rust 최소 버전, CI의 locked 빌드와 dependency advisory/license 검사를 관리한다. Cargo feature는 합쳐질 수 있으므로 보안 격리 경계로 취급하지 않는다. [Cargo resolver](https://doc.rust-lang.org/cargo/reference/resolver.html).

## 로컬 실행과 선택형 서버

### 1. 기본: 서버 없는 CLI

각 CLI 실행은 동일한 로컬 DB를 열고 짧은 트랜잭션으로 상태를 갱신한다. 브라우저는 CLI 종료 후에도 유지할 수 있도록 별도 프로세스로 실행한다. CLI가 죽었을 때 heartbeat를 누가 유지할지와 orphan 브라우저 처리 정책은 실행 모델에서 명시해야 한다. 장기 heartbeat 전담 프로세스를 몰래 필수화하지 않는다.

장시간 독점은 단순 TTL 하나로 처리하지 않는다. 프로필 소유는 프로세스 정체성과 OS 잠금, DB 상태를 함께 확인한다. PID는 재사용될 수 있으므로 시작 시각/프로세스 정체성 및 브라우저 프로필 경로 확인이 필요하며 플랫폼별 구현을 검증한다. 확인이 불가능하거나 충돌할 때 안전하게 거부하고 사용자가 진단할 수 있게 한다. 사용자 소유 브라우저를 자동으로 강제 종료하거나 잠금 파일을 임의로 지우지 않는다.

### 2. 선택: 로컬 서비스

`keyharbor serve` 같은 명령으로 하나의 관리 프로세스를 띄우고 CLI/MCP가 로컬 IPC로 연결한다. 서비스가 브라우저 프로세스, lease, heartbeat와 복구를 담당해 다중 클라이언트의 수명 관리가 단순해진다. Unix에서는 접근 권한이 제한된 Unix socket, Windows에서는 접근 제어가 설정된 named pipe를 후보로 한다. 동시 서비스 시작은 OS 잠금과 준비 상태 확인으로 조정한다. 데몬이 멈춰도 DB와 프로필은 보존하며 재시작 시 reconciliation을 수행한다.

두 모드가 **동시에 같은 프로필을 소유하지 못하도록** 동일한 DB 제약과 OS 프로필 잠금을 공유한다. CLI가 서비스를 발견하면 연결하는 정책과 명시적 오프라인 모드의 충돌 동작은 구현 전에 정한다. 로컬 IPC의 동일 사용자 접근은 보안 경계로 과장하지 않는다.

### 3. 선택: 원격 서버

원격 API는 로컬 서비스와 다른 배포·신뢰 모델이다. 기본적으로 네트워크 listener를 열지 않으며, 별도 활성화와 인증·암호화·권한·감사·백업 정책이 필요하다. 웹 접근 권한과 브라우저가 실제로 어느 호스트에 존재하는지 명시한다. 원격 사용자가 로컬 브라우저를 제어하면 프로필의 로그인 권한도 위임하는 것이다. 다중 호스트에는 공유 SQLite 파일 대신 서버를 통해 접근하거나, 필요 시 PostgreSQL 등 서버 DB를 별도 어댑터로 검토한다. 파일시스템의 브라우저 프로필은 DB 변경만으로 분산되지 않는다.

## 데이터와 상태

| 데이터 | 소유·저장 위치 | 주의점 |
|---|---|---|
| 비밀번호, API 키, TOTP | 사용자가 선택한 외부 금고 | KeyHarbor DB나 모델 응답으로 평문을 반환하지 않는 것이 목표. 각 금고 연동의 실제 능력 검증 필요 |
| 계정 참조·정책 | SQLite | 금고 항목 ID, 허용 origin, 선택한 프로필 등. 계정 이름과 도메인도 민감한 메타데이터 |
| 세션·lease | SQLite | 소유자, 상태, 프로필 ID, process identity, generation, 만료/heartbeat. 비밀번호·쿠키 금지 |
| 브라우저 프로필 | 로컬 전용 디렉터리 | 쿠키 외에도 저장소·캐시 등이 있다. 브라우저와 OS에 따라 보호 수준이 다르며 전체 암호화 보장 아님 |
| 로그 | 제한된 로컬 저장소 | 원칙적으로 이벤트와 식별자만. URL query, 토큰, 페이지 내용, 스크린샷, 비밀번호 기록 금지 |
| 선택적 작업 메모 | 별도 암호화된 앱 관리 데이터 후보 | MVP에서 기본 저장하지 않음. 저장 전 보존 기간·검색·삭제·백업 정책 결정 |

권장 상태: `created → starting → running → awaiting_user → running → stopping → stopped`; 실패는 `failed`, 재시작 후 확신이 없으면 `unknown/recovery_required`. `awaiting_user` 완료는 로그인 성공과 구분한다. 재부팅, 브라우저 충돌, 취소, 사용자 수동 종료를 각각 전이로 테스트한다.

## 병렬 처리·잠금 설계

1. SQLite의 짧은 write transaction에서 프로필당 활성 lease 하나라는 제약을 검사·생성한다. DB의 unique 제약을 최종 방어선으로 둔다. busy timeout과 제한된 재시도·명확한 오류를 적용하되 무한 대기하지 않는다.
2. 브라우저 실행이나 사용자 입력을 기다리는 동안 DB 트랜잭션을 유지하지 않는다. DB `starting` 기록 → commit → 프로필 OS 잠금 획득 및 프로세스 시작 → 결과를 조건부 갱신한다. 단계별 실패를 복구 가능한 상태로 남긴다.
3. OS 잠금은 열린 파일 핸들의 수명에 묶는다. 서버 없는 모드에서 잠금 보유자 프로세스가 브라우저보다 먼저 끝날 수 있으므로, 브라우저 프로세스 자체의 잠금과 실행 확인만으로 안전한지 검증하기 전에는 새 소유자를 자동 배정하지 않는다. 필요하다면 장기 감독 프로세스가 필요한 기능으로 명시한다.
4. lease에 owner와 무작위 generation/fencing 값을 둔다. 갱신·반환은 ID, owner, generation을 조건으로 compare-and-swap 한다. TTL이 지났어도 기존 브라우저가 살아 있으면 자동 재할당하지 않는다. DB fencing만으로 이미 연결된 CDP 클라이언트를 차단하지 못하므로 제어 채널 회수까지 필요하다.
5. 정상 종료 시 브라우저 종료 확인 → 프로필 잠금 해제 → DB 반환. 강제 중단 후에는 PID 재사용, orphan, OS 잠금, 프로필 경로를 확인하고 불확실하면 수동 복구 상태로 둔다. 다른 사용자의 프로세스를 죽이지 않는다.
6. 마이그레이션은 단일 실행자 잠금과 트랜잭션으로 수행하고 오류 시 원본 보존. SQLite 백업은 활성 WAL을 포함하는 일관된 백업 절차를 사용하며 DB 파일만 임의 복사하지 않는다. busy, 디스크 부족, 프로세스 kill, 전원 차단, 긴 read와 checkpoint를 검증한다.

## 인증 정보·암호화

### 1. 금고와 에이전트 사이

비밀은 외부 금고가 소유한다. KeyHarbor가 보유하는 것은 식별자와 최소 정책이다. 사용 요청에는 사용자, 작업/세션, 정확한 origin(스킴·호스트·포트), 금고 항목, 허용 동작, 만료를 연결한다. URL과 최종 대상 프레임은 실제 입력 직전에 검증하고, 교차 출처 iframe과 리다이렉트의 정책을 명시한다. 해당 기능을 금고 측이 강제할 수 없다면 통합 보안 보장을 주장하지 않는다.

초기에는 사용자가 브라우저에서 직접 로그인하는 흐름을 지원하고, 금고 자동 입력은 실제 브라우저 및 확장 연동의 대상 확인·오용 방지 시험이 끝난 다음 제공한다. API 키는 향후 별도 경로로 다룬다: 외부 금고가 목적지 제한된 요청을 대신 수행하는 방식이 후보이며, 환경 변수 주입은 자식 프로세스가 평문을 읽을 수 있다. 마스킹은 보조 수단이며 미지의 변형이나 응답 내 새 비밀을 모두 제거하지 못한다.

### 2. 앱이 소유한 암호화 데이터

MVP에서 비밀번호 금고와 프로필 아카이브를 만들지 않으므로 자체 범용 암호화 저장소는 필수가 아니다. 민감한 앱 관리 데이터를 저장해야 한다면 검증된 라이브러리의 AEAD로 암호화하고, 난수 nonce의 유일성·포맷 버전·key ID·레코드 종류/식별자의 associated data를 명세한다. OS 암호학적 난수로 생성한 데이터 키와 OS 키 저장소의 보호를 검토한다. 키가 없으면 기존 데이터를 덮는 새 키를 만들지 않고 잠긴 상태로 오류를 낸다. 백업 키, 키 유실, 교체·재암호화와 이전 백업의 복구를 구현 전에 정한다. 직접 암호 알고리즘을 구현하지 않는다. [OWASP 암호화 저장](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html).

예: macOS Keychain은 소량의 비밀과 암호화 키를 저장하고 접근 조건을 설정하는 수단이다. 실제 코드 서명, 접근 제어, 잠금 상태와 백그라운드 동작은 검증해야 한다. Linux/Windows의 동등 기능과 실패 시 동작은 별도 설계한다. 키를 같은 디렉터리의 평문 파일에 조용히 대체 저장하지 않는다. [Apple Keychain](https://developer.apple.com/documentation/security/keychain-services).

### 3. 브라우저 프로필의 한계

Chrome은 실행 중 프로필 디렉터리를 직접 사용한다. KeyHarbor가 DB나 별도 파일을 암호화해도 프로필의 모든 파일이 앱 키로 암호화되는 것은 아니다. 기본안은 OS 디스크 암호화, 사용자별 파일 권한과 브라우저 자체 보호에 의존하며 보장 범위를 플랫폼별로 표시한다. 앱 차원의 암호화 아카이브는 브라우저 종료 후 생성할 수 있으나 실행 중 평문 작업 디렉터리, 충돌 잔여물, swap·백업, OS에 묶인 쿠키 키와 복원 가능성 문제가 남는다. 이 기능은 MVP에서 제외한다.

Chrome의 remote debugging은 로그인 쿠키 등 강한 접근 권한을 준다. Chrome 136부터 기본 데이터 디렉터리에 debugging 스위치를 적용할 수 없고 별도 user-data-dir이 요구된다. [Chrome 공식 설명](https://developer.chrome.com/blog/remote-debugging-port). 전용 프로필을 기본으로 하고, 일반 브라우저 연결은 별도 동의와 위험 설명이 필요하다. 로컬 CDP 포트나 endpoint를 에이전트에 직접 주면 세션 전권을 위임하므로 도메인 제한을 약속할 수 없다. 초기에는 신뢰된 클라이언트에 한정하고 정책 강제가 필요한 경우 직접 endpoint를 노출하지 않는 중개 경로를 따로 설계·검증한다.

## 저장·복구와 운영

- 플랫폼별 사용자 전용 데이터 디렉터리에 DB, 프로필, 최소 이벤트를 분리하고 권한을 제한한다. 심볼릭 링크와 경로 이탈을 검증한다.
- 삭제는 DB 항목, 브라우저 프로필, 외부 금고, 백업, 서버 측 로그인 무효화가 별개다. 기본 삭제 범위를 명확히 하고 관련 없는 파일을 건드리지 않는다. SSD나 백업의 물리적 완전 삭제는 보장하지 않는다.
- 세션 종료는 서버 측 로그아웃을 의미하지 않는다. 토큰 폐기나 로그아웃은 사이트별로 다르다.
- 버전 업그레이드 시 DB와 프로필 형식 호환성을 확인한다. 프로필은 다른 OS·사용자·기기로 옮겼을 때 복호화나 재인증이 필요할 수 있다.
- 최소 로컬 이벤트에 생성·할당·인계·해제·오류 코드와 시각을 남기되 비밀과 본문을 남기지 않는다. 로그 접근 권한과 보존 기간을 지정한다.

## 검증 게이트

1. 테스트용 사이트에서 사용자 수동 로그인 → 정상 종료 → 재실행. 쿠키·localStorage·IndexedDB·sessionStorage·passkey·서버 만료를 구분해 기록한다.
2. 여러 독립 CLI 프로세스로 같은 프로필 동시 할당을 반복해 성공자가 정확히 하나인지 확인한다. 서로 다른 프로필은 병렬로 동작해야 한다.
3. 생성 중 kill, 브라우저만 생존, PID 재사용, 디스크 부족, DB busy, 중단된 migration, OS 재부팅을 시험한다. 불확실할 때 다른 프로세스를 종료하거나 프로필을 덮어쓰지 않아야 한다.
4. 서비스 미실행·동시 시작·서비스 충돌·재시작·직접 CLI와 서비스 경쟁을 실험한다. 로컬 IPC의 접근 범위와 에러를 확인한다.
5. 금고 통합 시 테스트 계정으로 잘못된 origin/iframe/리다이렉트, 모델 응답·로그·오류 메시지의 유출, 권한 만료를 확인한다. 같은 OS 사용자 악성 프로세스는 별도 위협으로 평가한다.
6. 부하 조건(동시 세션 수, 초당 상태 변경 수, 응답 시간 목표)을 정한 뒤 SQLite와 필요 시 PGlite/PostgreSQL을 같은 작업으로 측정한다. 현재는 성능 우위에 대한 측정 결과가 없다.

## 열린 결정

- 최초 지원 OS와 배포 방식, 브라우저 종류.
- 서버 없는 CLI에서 장시간 브라우저 소유를 누가 감독할지. 안정적 lease 유지가 필수면 선택형 로컬 서비스가 사실상 권장될 수 있다.
- MCP를 세션 관리에만 쓸지, 브라우저 조작도 중개할지. 직접 CDP 제공은 정책 강제와 양립하기 어렵다.
- 금고별 연동의 실제 입력 방식과 사용자 승인, 작업별/사이트별 권한 제공 가능성.
- 작업 메모와 URL 등 메타데이터의 암호화 필요성, 검색과 복구 정책.
- 원격 배포를 실제로 제공할지, 다중 사용자와 호스트 범위.

# KeyHarbor

상태: 초기 프로토타입. 아래의 구현 범위와 제한을 확인하세요.

## 빠른 시작 (macOS)

Rust 툴체인과 Google Chrome이 필요하다. 브라우저는 기존 사용자 프로필이 아닌 KeyHarbor 전용 프로필로 열린다.

```sh
cargo build --locked
./target/debug/keyharbor create work
./target/debug/keyharbor list
./target/debug/keyharbor open <session-id>
# 또는 사이트를 함께 열기
./target/debug/keyharbor open <session-id> --url https://example.com/login
```

열린 창에서 사용자가 로그인할 수 있다. `wait-auth <session-id>`는 인증 대기와 요청 ID를 기록한다. 사용자는 `handoff <session-id>`로 현재 요청 ID를 조회하고 `resume <session-id> <request-id>`로 해당 요청의 재개를 기록한다. 이전 요청 ID로는 새 요청을 재개할 수 없다. 이전 버전의 `resume <session-id>` 호출에는 요청 ID를 추가해야 한다. `stop <session-id>`는 종료 요청을 기록하며, 창을 직접 닫으면 감독 프로세스가 종료를 감지한다. 이후 같은 ID로 다시 열면 같은 프로필을 사용한다. `--browser <executable>`로 다른 실행 파일을 지정할 수 있으나 Chrome 외 호환성은 검증하지 않았다.

인증 요청 시 `wait-auth <session-id> --origin https://example.com`으로 사이트 출처를 선택적으로 기록할 수 있다. MCP의 `session_wait_auth`에도 선택적 `origin`을 전달한다. 경로·쿼리·fragment·사용자 정보는 허용하지 않으며 HTTPS 또는 로컬 HTTP만 받는다. `handoff` 출력의 네 번째 항목에서 출처를 확인한다. 이는 요청자가 제공한 정보이며 실제 브라우저 탭이나 리다이렉트와 일치하는지 검증하지 않는다. 출처는 SQLite에 평문으로 저장되므로 도메인 자체가 민감할 수 있다. 인증하기 전에 사용자가 브라우저 주소를 직접 확인해야 한다.

선택적 시작 URL은 HTTPS 또는 로컬 호스트의 HTTP만 허용하며 사용자 정보, 쿼리, fragment가 있으면 거부한다. URL은 브라우저 프로세스의 인자로 전달되므로 경로에도 비밀번호·토큰을 넣지 않는다. URL은 방문 시 브라우저 기록에 남을 수 있다. 이 제한은 대상 사이트나 이후 리다이렉트의 안전성을 보증하지 않는다.

### 금고 항목 참조

중지된 세션에 사용할 OpenKeylet 항목 이름을 기록할 수 있다.

```sh
./target/debug/keyharbor bind-account <session-id> '항목 이름'
./target/debug/keyharbor account <session-id>
./target/debug/keyharbor unbind-account <session-id>
```

이는 사용자가 지정한 **이름 참조**다. KeyHarbor는 OpenKeylet에 접속하거나 해당 항목의 존재·사이트 일치 여부를 확인하지 않고, 비밀번호를 가져오거나 입력하지 않는다. 사용자는 실제 브라우저의 금고 확장에서 사이트와 항목을 확인해야 한다. 참조는 중지된 세션에서만 변경할 수 있다. 이름은 SQLite에 평문으로 저장되고 `session_account` MCP 도구를 통해 연결된 클라이언트에 노출된다. 항목 이름 자체가 민감할 수 있으며, 이 인자에는 비밀번호나 토큰을 입력하지 않는다.

기본 데이터 경로는 `~/.keyharbor`다. `--data-dir <path>` 또는 `KEYHARBOR_HOME`으로 변경할 수 있다. 기존 데이터 디렉터리는 다른 사용자에게 접근 권한이 없어야 한다. SQLite DB와 브라우저 프로필은 민감한 로컬 데이터다.

브라우저 시작 시 `profiles` 디렉터리와 해당 세션의 프로필 경로가 심볼릭 링크이거나 디렉터리가 아니면 실행을 거부한다. 이 검사는 우발적인 경로 변경을 막기 위한 것으로, 같은 OS 사용자가 검사와 브라우저 실행 사이에 경로를 바꾸는 공격까지 방어하지는 않는다. 기존 경로를 자동으로 삭제하거나 교체하지 않는다.

### 세션 메타데이터 백업

```sh
./target/debug/keyharbor backup /private/backup/keyharbor.sqlite3
```

실행 중인 SQLite의 커밋된 내용을 온라인 백업한다. 대상 디렉터리는 미리 만들어야 하며 같은 디렉터리에서 하드 링크를 지원해야 한다. 대상 파일이 이미 존재하면 덮어쓰지 않는다. Unix에서는 백업 파일을 사용자 전용 권한으로 만들며, 백업은 암호화되지 않는다. 세션 이름, 계정 참조, 인증 요청과 사이트 출처 등 민감한 메타데이터가 포함될 수 있으므로 백업 경로와 보관을 직접 보호한다.

이 명령은 브라우저 프로필, 쿠키, 금고, 브라우저 프로세스나 로그인 상태를 백업하지 않는다. 실행 중 세션의 상태도 스냅샷에 기록되므로 원본 DB를 실행 중에 교체하거나 백업만으로 브라우저를 복원하지 않는다. 자동 복원 기능은 아직 없다. 프로세스가 백업 도중 강제 종료되면 대상 디렉터리에 `.keyharbor-backup-`으로 시작하는 불완전한 임시 파일이 남을 수 있다.

## 로컬 MCP 연결

빌드한 실행 파일을 MCP 클라이언트의 stdio 서버로 등록한다. 다음은 명령과 인자의 예이며 설정 파일 형식은 클라이언트에 따라 다르다. 실행 파일 경로는 실제 절대 경로로 바꾼다.

```json
{ "command": "/absolute/path/to/keyharbor", "args": ["mcp"] }
```

기본 macOS Chrome 대신 다른 실행 파일을 사용하려면 서버를 등록하는 사용자가 `args`를 `["mcp", "--browser", "/absolute/path/to/browser"]`로 지정할 수 있다. 이 경로는 실행 파일이므로 신뢰할 수 있는 브라우저만 지정한다. 에이전트가 MCP 도구 인자로 실행 파일을 바꿀 수는 없다.

하나의 에이전트 연결을 특정 세션에 한정하려면 사용자가 미리 세션을 만들고 서버 인자를 `["mcp", "--session", "<session-id>"]`로 설정한다. 이 MCP 서버는 해당 세션만 목록에 표시하고 다른 세션의 조회·열기·인증 대기·대기·종료·CDP 주소 요청과 새 세션 생성을 거부한다. 같은 세션에 대한 범위 지정 MCP 서버는 한 번에 하나만 실행할 수 있다. 범위를 지정하지 않으면 모든 세션에 접근할 수 있다. 범위 미지정 서버, 다른 셸·DB 접근이나 이미 발급된 CDP 연결은 이 잠금으로 제한되지 않는다. 같은 OS 사용자로 실행되는 악의적인 클라이언트에 대한 격리는 제공하지 않는다.

세션 목록·생성·열기·인증 대기·종료 요청과 사용자가 지정한 금고 항목 이름 조회를 제공한다. `session_open`의 선택적 `url`로 시작 사이트를 지정할 수 있다. 세션 이름과 상태는 클라이언트에 노출되므로 이름에 비밀번호나 토큰을 넣지 않는다. MCP를 연결한 클라이언트는 해당 사용자 데이터 디렉터리의 모든 세션을 관리할 수 있다. 신뢰할 수 있는 클라이언트에만 연결한다. MCP는 인증 재개, 사이트 로그인 성공 검증, 자격 증명 조회, 강제 복구를 제공하지 않는다. 사용자가 CLI에서 재개를 기록한다.

`session_wait_auth`로 대기 상태를 기록하면 요청 ID가 반환된다. 같은 ID를 `session_wait_for_resume`의 필수 인자 `request_id`에 전달해 해당 요청의 재개를 기다릴 수 있다. `timeout_seconds`는 1~300초이며 생략하면 120초다. 타임아웃은 대기 호출만 끝내고 세션 상태를 바꾸지 않는다. 새 인증 요청이 이전 요청을 대체하거나 감독자가 사라지거나 실행 generation이 바뀌면 오류를 반환한다. 이 도구는 인증 성공이나 재개한 사람의 신원을 확인하지 않는다. 사용자는 CLI의 `handoff <session-id>`로 요청 ID를 확인하고 `resume <session-id> <request-id>`로 재개 상태를 기록할 수 있다.

MCP 도구에서 `session_resume`을 제거해 대기와 사용자 재개를 구분한다. 기존 호출자는 사용자가 CLI에서 `resume`을 실행하고 MCP 클라이언트가 `session_wait_for_resume`으로 기다리는 방식으로 바꿔야 한다. 다만 에이전트가 같은 OS 사용자로 셸이나 DB에 접근할 수 있다면 CLI를 직접 실행하거나 상태를 변경할 수 있으므로, 이는 악의적인 에이전트를 막는 보안 경계가 아니다.

### 선택형 브라우저 자동화 연결

기본적으로 브라우저 제어는 꺼져 있다. 직접 CLI로 사용할 때는 `open <session-id> --cdp`로 실행하고, 브라우저가 준비된 뒤 `endpoint <session-id>`로 WebSocket 주소를 확인한다. MCP 서버에서 사용하려면 사용자가 서버 인자를 `["mcp", "--allow-cdp"]`로 구성하고, 각 `session_open` 호출에 `"cdp": true`를 명시한다. 생략하거나 `false`로 지정한 세션에는 CDP가 켜지지 않는다. `session_endpoint`로 주소를 요청할 수 있으며, 아직 준비되지 않았다면 잠시 후 다시 요청한다. 이전 버전에서 `--allow-cdp`만으로 열던 세션도 이제 `"cdp": true`가 필요하다.

**CDP는 해당 브라우저의 모든 탭과 로그인된 계정에 대한 강한 권한이다.** 로컬 디버깅 포트에는 KeyHarbor의 별도 인증이나 사이트별 제한이 없다. 같은 컴퓨터의 다른 프로세스도 접근할 수 있으며, 신뢰할 수 있는 환경과 클라이언트에서만 사용한다. `wait-auth` 중 새 주소 조회는 거부하지만 이미 연결된 클라이언트는 끊지 않는다. 비밀번호 입력이나 2차 인증을 비공개로 처리해야 한다면 CDP가 활성화된 브라우저에서 안전하다고 가정하지 않는다. 브라우저 종료 전까지 연결을 철회하는 기능은 없다.

인증 입력 시 CDP 노출을 줄이려면 먼저 CDP 없이 세션을 열어 사용자가 로그인하고, 브라우저를 닫아 상태가 `stopped`인지 확인한 다음 같은 세션을 CDP로 다시 열 수 있다. Chrome 프로필의 로그인 상태가 유효하면 재사용되지만, 브라우저를 재시작하므로 열린 탭과 진행 중인 페이지 작업의 복원은 보장되지 않는다. `--allow-cdp`는 MCP 클라이언트가 CDP 사용을 요청할 권한을 주며, 세션별 `cdp` 옵션은 악의적인 클라이언트에 대한 승인 경계가 아니다.

주소는 현재 세션 generation, 실행 상태 및 감독 잠금을 확인한 후 반환한다. 이는 로컬 공격자로부터 포트를 보호하거나 브라우저의 생존과 주소 소유권을 완벽하게 증명하는 인증 수단은 아니다. Chromium 기반 브라우저의 `DevToolsActivePort`를 사용하며 다른 브라우저와의 호환성은 확인하지 않았다.

검증: MCP 프로토콜 테스트에서 가짜 브라우저로 생성·열기·중복 할당 거부·인증 대기·재개·종료를 확인했다. Codex CLI는 명령행으로 전달한 서버 설정을 정상적으로 읽었다. Claude Code CLI는 격리된 임시 사용자 설정의 MCP 서버를 `Connected`로 확인했으며, 별도 임시 프로젝트 설정은 승인 대기로 표시했다. 두 에이전트가 실제 작업에서 MCP 도구를 호출하는 전체 흐름은 아직 검증하지 않았다.

Claude Code CLI가 설치된 환경에서는 `KEYHARBOR_BINARY=/absolute/path/to/keyharbor python3 tests/claude-mcp-health.py`로 임시 설정을 이용한 연결 확인을 재현할 수 있다. 이 검사는 모델 호출 없이 MCP 연결 상태만 확인한다.

현재 제한:

- 실행·인증 대기·종료 중 감독 프로세스가 비정상 종료되면 목록에 `recovery_required`로 표시된다. 시작 중 중단된 세션은 `starting`에 남을 수 있다. 인증 대기·재개·종료 요청은 감독자가 없으면 거부하며 자동으로 브라우저를 종료하지 않는다. 먼저 해당 프로필을 사용하는 브라우저 프로세스가 모두 종료됐는지 직접 확인한 뒤 `recover <session-id> --confirm-browser-closed`로 상태를 복구할 수 있다. 감독자가 살아 있으면 복구가 거부된다. 잠금 확인은 조회 시점의 상태이며 브라우저 종료 여부나 프로세스 신원을 자동으로 증명하지 않으므로 확인 없이 복구하면 프로필이 충돌할 수 있다.
- 인증 대기와 재개는 상태 전환일 뿐 로그인 성공을 확인하지 않는다. 금고 자동 연동, CDP 접근 정책 강제, 선택형 서버는 아직 구현되지 않았다. OpenKeylet 확장의 수동 입력은 별도 합성 통합 시험을 했으며 [결과와 범위](docs/openkeylet-integration.md)를 확인한다.
- SQLite의 중복 할당과 감독 프로세스 잠금은 KeyHarbor가 관리하는 동일 세션에만 적용된다. 브라우저 프로필 전체의 암호화나 외부 프로세스에 대한 격리는 보장하지 않는다.
- 가짜 브라우저를 이용해 다중 CLI 할당과 상태 전환을 테스트했다. 로컬 HTTP 테스트 페이지와 headless Chrome for Testing 및 설치된 일반 Chrome으로 두 프로필의 쿠키·localStorage·IndexedDB 격리와 재실행을 확인했다. MCP 합성 인증 흐름과 감독 프로세스 중단 후 수동 복구도 두 브라우저에서 시험했다. 일반 Chrome의 확장 연동 시험은 실행 옵션에 따라 실패와 성공이 나뉘었으며 [상세 결과](docs/openkeylet-integration.md)를 확인한다. 실제 사이트 로그인, 화면 조작, Chrome 자체 충돌과 OS 재부팅 복구는 아직 검증하지 않았다.

### 실제 브라우저 합성 시험

빌드된 KeyHarbor, Playwright의 `index.mjs`와 해당 버전에 맞는 Chrome for Testing을 별도로 준비하고 실행한다. 시험은 임시 프로필과 로컬 HTTP 서버를 사용한다.

```sh
KEYHARBOR_BINARY=/absolute/path/to/keyharbor \
KEYHARBOR_TEST_PLAYWRIGHT=/absolute/path/to/playwright/index.mjs \
KEYHARBOR_TEST_CHROME='/absolute/path/to/Chrome for Testing' \
node tests/browser-isolation.mjs
```

같은 환경 변수로 `node tests/mcp-browser-interop.mjs`를 실행하면 MCP 세션 생성·브라우저 연결·합성 인증 대기와 재개·로그인 상태가 필요한 페이지 접근, CDP 없이 합성 로그인 후 같은 프로필을 CDP로 재실행하는 흐름을 확인한다. 합성 쿠키가 시험 중 MCP 응답과 KeyHarbor SQLite 파일에 나타나지 않는지도 확인한다.

`node tests/browser-recovery.mjs`는 테스트가 생성한 감독 프로세스의 명령과 세션 ID를 확인하고 강제 종료한다. 브라우저가 살아 있는 동안 재할당 및 새 주소 조회가 거부되는지 확인하고, 브라우저 프로세스 종료 후 복구해 프로필 데이터를 확인한다. 현재 시험 결과는 macOS의 headless Chrome for Testing과 일반 Chrome에서 확인했다.

이 시험들은 선택형 CDP 연결을 켜고 Playwright로 로컬 페이지를 조작한다. 인증 대기 중에도 이미 연결된 CDP 클라이언트는 계속 접근할 수 있음이 재현됐다. 합성 시험의 비밀 비노출 확인은 다른 로그, 브라우저 프로필, 프로세스 메모리나 실제 에이전트 전체에 대한 보장이 아니다. 시험 자료는 임시 디렉터리에 남는다.

## 개요

Codex, Claude Code 등 기존 AI 에이전트가 여러 웹 작업을 병렬로 수행할 때 비밀번호와 계정, 브라우저 프로필, 로그인 상태와 작업 맥락을 관리하는 무료 로컬 설치형 통합 솔루션. Browser Use와 Computer Use 등 기존 브라우저 조작 도구를 돕는 CLI로 구상하며, 브라우저와 AI 모델을 새로 만들지 않는다. 비밀번호 금고를 직접 구현할지 기존 도구와 연동할지는 검토가 필요하다.

## 문제

- 여러 작업이 하나의 브라우저와 계정을 공유하면 탭과 로그인 상태가 섞일 수 있다.
- 브라우저를 다시 열거나 인증이 만료되면 작업을 이어가기 어렵다.
- 인증 대기, 실패와 사용자 개입이 필요한 시점을 여러 에이전트 사이에서 추적하기 어렵다.
- 폼 입력이나 프로필 이미지 업로드가 사이트마다 달라 작업이 중단될 수 있다.

## 구상하는 기능

- 작업별 독립 브라우저 프로필 생성, 병렬 실행, 상태 조회, 종료와 재개.
- 세션별 탭, 북마크, 메모와 작업 결과 저장 및 복원.
- 인증 상태의 임시 보관과 보관 기한 관리. 사이트 측 만료는 별도로 확인하고 필요하면 재인증.
- OpenKeylet 등 외부 비밀번호 관리자 연동 검토. 인증 정보 사용 기록과 알림.
- 인증 메일 확인, 사용자 개입 및 재개 흐름. CAPTCHA나 기기 인증 등은 직접 처리할 수 있다.
- 폼 필드와 상태 인식, 입력 결과 확인, 이미지 파일 업로드와 붙여넣기 지원 검토.
- CLI와 MCP를 통한 Codex·Claude 연결. 실행·대기·완료·실패 상태와 활동 기록 표시.

## 예상 사용 흐름

1. 에이전트가 작업별 브라우저 세션을 요청한다.
2. CLI가 해당 프로필과 작업 맥락을 열고 에이전트에 연결한다.
3. 로그인이 필요하면 기존 인증 상태를 확인하고 필요할 때 금고와 인증 수단을 이용한다.
4. 인증이나 사이트 조작이 막히면 사용자에게 알리고, 처리 후 같은 작업을 이어간다.
5. 작업 결과와 북마크를 저장하고 세션 상태를 기록한다.

## 검증할 점

- 기존 Chrome 연결과 별도 프로필 실행에서 각각 계정 격리와 병렬 연결이 가능한 범위.
- 쿠키뿐 아니라 사이트별 저장소와 기기 인증이 세션 복원에 미치는 영향.
- OpenKeylet과 브라우저 조작 도구의 연동, 비밀번호가 모델 문맥이나 로그에 노출되지 않는 경로.
- 인증 정보와 세션 데이터의 암호화, 접근 통제, 만료·삭제 및 기록 범위.
- 이미지 붙여넣기와 파일 업로드, 이메일 인증, 폼 인식의 실제 사이트별 동작.
- 기존 브라우저 자동화 도구와 차별화되는 계정·병렬 실행·사용자 개입 경험.
